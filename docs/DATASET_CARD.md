## What one sample is

- One or two PNG renders (512×384) of a procedural scene, drawn by the same renderer the app uses.
- A question with 2–3 admissible one-word answers.
- An oracle answer computed from the scene geometry, with ray-cast visibility.

Images are rendered in headless Chrome through the app's own render target (`?render=1`).

## Task types

| Task | Frame | Answers | Rule (docs/CONVENTIONS.md) |
|---|---|---|---|
| `lateral` | camera | left / right / unknown | bearing order in the camera frame |
| `depth` | camera | closer / farther / unknown | range from the optical centre |
| `vertical` | upright viewer | above / below / unknown | gravity-aligned height |
| `visibility` | camera rays | visible / occluded | unoccluded fraction of the in-frame silhouette |
| `obs_lateral` | observer | left / right / unknown | object's bearing in an oriented agent's own frame |
| `obs_frontback` | observer | front / behind / unknown | same, front/back axis |
| `facing` | camera + heading | toward / away | angle between the agent's heading and the direction to the camera |
| `abstain` | any | **unknown** | the question names an object that is ≤ 3% visible but in frame, so it cannot be answered from the image |
| `mv_best_view` | two views | first / second | which view shows more of the object (Δ ≥ 0.4 in unoccluded fraction) |
| `mv_camera_motion` | two views | left / right | which way the camera orbited between views (25°–110°) |

Ties inside the tolerances, and questions about objects that are partly hidden or out of frame, are
excluded rather than labelled.

## Record layout

```
images/<split>/<sha256[:20]>.png   opaque names, unrelated to pose or answer
registry/<split>.jsonl             full record, private: oracle answer, explanation, scene spec, cameras, hashes, provenance
model_inputs/<split>.jsonl         {sample_id, image_paths, prompt}: the only thing a model may see
sft/<train|val>.jsonl              chat-format supervision with the image(s), the prompt, the one-word target
manifest.json                      config, counts, label balance
holdout.lock.json                  frozen test ids, scene fingerprints, image hashes, registry digests
```

The prompt contains no digits, coordinates, poses, seeds, fingerprints, explanation text or answers.
`research/scripts/validate_dataset.py` and the unit tests enforce this.

## Splits and the locked holdout

| Split | Seeds | Templates | Lighting | Camera range | Object types |
|---|---|---|---|---|---|
| train | `…/train/…` | families 0, 1 | studio, warm, dim | 70% of the allowed range | held-out nouns excluded |
| val | `…/val/…` | 0, 1 | same | same | excluded |
| test_iid | `…/test_iid/…` | 0, 1 | same | same | excluded |
| test_ood | `…/test_ood/…` | **2 only** | **backlit only** | **full range** | **held-out nouns allowed** (candle, speaker, ottoman, beanbag, lantern, bucket) |

How the holdout is protected:
- Test splits are built first and locked by SHA-256 of their registry files.
- Rebuilding refuses to touch them unless `--relock` is passed, and refuses any train or val scene or
  image that collides with the lock.
- Training, teacher collection and hard-example mining call `assert_not_holdout` and refuse locked ids
  and images.

Pilot balance: every binary task is within 45–55% per label in every split, except camera motion on
the small splits (see `manifest.json`).

## Known limitations

- Synthetic primitives only. Expect a large gap to photographs.
- Agents are toy robots whose facing is shown by a visor, chest panel and feet. Seats (sofa, armchair,
  chair) also have a front. Facing is judged from the image alone.
- One question family per relation per template. Paraphrase diversity is limited.
- Visibility uses a 20×20 ray grid per object.
- Abstention samples are a few percent of the data.
